Final Decision
Option 3 — Best of Both, Merged into One
Idea 2 wins on architecture depth by a wide margin. But Idea 1 has one feature that Idea 2 completely lacks: GitHub semantic search and real-world module extraction. This is not a cosmetic feature — it fundamentally validates AI-generated module lists against actual production codebases. The merged architecture takes Idea 2's entire engine and inserts Idea 1's GitHub intelligence as Phase 1 Step 7 (the Module Intelligence Layer), plus brings back the live pipeline visualization as the user-facing experience layer. The result: the only version worth building.
Think of it this way: Idea 2 is the brain — it knows how to think, score, question, and output. Idea 1 is the eyes — it can look at the real world and validate what the brain came up with against thousands of real projects. Neither alone is complete. Together, the system doesn't just guess what modules a project needs — it confirms those modules against production codebases that already solved similar problems.
Phase 0

Pre-Flight Checks

Before a single AI call is made, the system must check for two conditions that would make any output meaningless: a completely missing core intent, and input so thin that nothing can be extracted from it.

Think of Phase 0 as the airport security check. You don't board the plane first and then check if you have your passport. You check before anything else starts. If the absolute minimum isn't there, the system stops and asks for it specifically — not with a generic "tell me more" but with a targeted question that directly addresses what's missing.
B0

BLOCKER Pre-Check — Project Goal (P-01) & Core Features (P-03)

runs before everything. loop counter does not increment. output is impossible until resolved.
BLOCKER

What it does: The system checks whether P-01 (the fundamental problem the software solves) and P-03 (any core features) can be detected at all from the raw input. This is not a quality check — it is an existence check. If the input is something like "I want to build an app" with zero context about what it does, P-01 is MISSING.

Condition: If P-01 or P-03 is MISSING, skip domain classification, skip chunking, skip GitHub search, skip all pipeline steps. The system shows only the BLOCKER question for the missing parameter. This is called a pre-round — it does not count against the maximum round counter. The confidence ceiling is hard-locked at 40% until resolved, and no scope output is generated regardless of round count.

BLOCKER question format — P-01 (Problem Goal)
  • Question shown: "What problem does this software actually solve? Pick the closest description." — with MCQ options: Automate a manual process / Replace an existing tool / Connect two systems / Sell a product or service to customers / Give internal teams a better workflow / Other (describe).
  • If user picks one or types custom: P-01 is now at minimum PARTIAL-THIN. BLOCKER lifts. System proceeds to Step B1 (Thinness Check) and then to Step 1.
  • If user skips or gives gibberish: BLOCKER question repeats with a different framing. Extended BLOCKER rounds (more than 3 attempts) trigger a manual review flag.
B1

Thinness Pre-Check — Input Density Measurement

measures token count, keyword hits, and entity density before committing to the full pipeline.
FROM IDEA 2

What it does: Even if P-01 and P-03 exist, the input may be so thin that semantic chunking and hybrid search will produce unreliable results. This step measures three signals: raw token count, keyword hit density (how many of the base parameter keywords appear), and named entity density (how many proper nouns, product names, domain terms).

Thinness Thresholds
// Any two of three signals below threshold → thinness triggered
Token count < 80 tokens → THIN signal 1
Keyword hits < 2 (from base parameter keyword list) → THIN signal 2
Named entities < 1 (no product names, role names, or domain terms found) → THIN signal 3
// Response if THIN:
Ask one targeted question based on closest domain match signal
Not "tell me more" — quote what's missing: "Target users weren't mentioned — who will use this?"
// Thinness round does NOT count against max_rounds

Why this matters: If you run the full pipeline on "I want a food app", the vector embeddings are almost meaningless, BM25 hits nothing specific, and the GitHub search returns random results. One targeted question at this stage can turn a 6-word input into a 50-word input that actually yields useful results from the pipeline.

Phase 1

Intelligence Gathering

The system collects every available signal from the input: domain, parameter states, semantic content, and — uniquely — real-world module patterns from GitHub's production codebase library.

Think of Phase 1 as the research phase. Before a consultant gives a proposal, they study the client's industry, look at how similar companies have solved similar problems, and identify exactly what information they have and what's still missing. This phase does all of that — automatically, in seconds.
01

3-Signal Domain Classification

keyword density + named entity recognition + llm micro-call. multi-domain support included.
FROM IDEA 2

What it does: Determines which of the 9 supported domains this project belongs to. The domain determines which extra parameters get added, what the confidence threshold is, what the MCQ question options look like, and which GitHub repositories get searched. Getting the domain right is the most important single classification step in the entire pipeline.

3-Signal Classifier Formula
// Signal 1: Keyword density (40% weight)
keyword_score[domain] = (domain_keywords_found / total_domain_keywords) × 100
// Signal 2: Named Entity Recognition (35% weight)
ner_score[domain] = confidence from NER model over domain-specific entities
// e.g., "Stripe, Razorpay, invoice" → FinTech entities
// Signal 3: LLM micro-call (25% weight) — only if ambiguous
if (keyword_score[top] − keyword_score[second] < 15):
  llm_score = one Claude call: "Is this SaaS, FinTech, Marketplace, or other?"
// Combine signals
domain_confidence = keyword_score×0.40 + ner_score×0.35 + llm_score×0.25
// Soft confidence bands
≥ 65% → confirmed domain, load template
44–64% → probable domain, load template with confirm flag
< 44% → Custom / Other fallback
// Multi-domain: if top 2 domains both ≥ 45%, merge their extra parameters
multi_domain = (domain_1_score ≥ 45%) AND (domain_2_score ≥ 45%)

Domain classification is the system's first big bet. Once it knows the domain, everything else becomes domain-aware — the questions asked, the GitHub repos searched, the extra parameters loaded, the effort multipliers applied. Getting this right once saves hours of misaligned output later.
02

Semantic-Aware Sliding Window Chunking

detects topic boundaries via embedding cosine similarity. never cuts a topic mid-thought.
FROM IDEA 2

What it does: Splits the project description into chunks that align with topic boundaries, not fixed token counts. The core insight: a project description is written in natural topics — "For payments, we need..." then "The admin section should..." then "Users need to be able to...". Each of these should be one chunk. Cutting at 512 tokens regardless of meaning destroys this.

Semantic Chunking Algorithm
// Step A: tokenize into sentences
sentences = tokenize(input)
// Step B: embed adjacent sentence pairs
for i in range(len(sentences) - 1):
  similarity[i] = cosine_sim(embed(sentences[i]), embed(sentences[i+1]))
// Step C: detect topic breaks where adjacent sim drops below threshold
topic_break_threshold = 0.65
if similarity[i] < 0.65 → new chunk starts at sentences[i+1]
// Step D: handle edge cases
if chunk_tokens > 512 → apply RCS (recursive character splitting) within topic
if chunk_tokens < 40 → merge with next chunk
if total_input_tokens < 200 → single chunk, skip vector path entirely
// Guarantee: every token in input appears in exactly one chunk (no orphan text)

Short input fallback: If total input is under 200 tokens, vector embeddings are too noisy to be useful. The system uses BM25 + Query Expansion only, plus a lightweight LLM paragraph labeller that categorises each sentence as Feature / Constraint / Unclear / Off-Topic and maps them to parameter buckets. Full hybrid search re-activates automatically when the user adds context in round 1.

03

Hybrid Search — Vector + BM25 + Query Expansion + Cross-Encoder

four-stage retrieval per parameter. rrf merge keeps it scale-robust. cross-encoder gives final precision.
FROM IDEA 2

What it does: For each parameter (P-01 through P-09 plus domain extras), the system finds the most relevant chunks from the project description. This is not searching the internet — it is searching the chunks of the input itself, to determine what was said (or not said) about each parameter.

Four-stage retrieval pipeline — runs for every parameter
① Semantic Chunks
Embed all chunks with MiniLM-L6-v2
Build FAISS vector index
Query: parameter description embedding
Top-5 results per parameter
→
② BM25 + Expansion
Build BM25 inverted keyword index
Load synonym table from parameters.json for domain
"payment" → also queries: billing, checkout, invoice, gateway, transaction
Top-5 BM25 results per parameter
→
③ RRF Merge
Reciprocal Rank Fusion: score = Σ 1/(60 + rank)
Combines Vector-5 + BM25-5
Top-10 merged list per parameter
Scale-robust: no magnitude normalisation needed
→
④ Cross-Encoder Re-rank
Read all top-10 chunks together
One Claude call per parameter for relevance re-ranking
Final top-3 chunks → State Scorer
Only on top-10, not all chunks. Precision gain for small cost.
The hybrid search is doing something subtle but powerful: it is reading the project description like a detective, asking "did this client tell us anything about authentication? About integrations? About budget?" — and doing it simultaneously for every parameter that matters for this domain. The combination of semantic similarity and keyword matching ensures nothing gets missed just because the client phrased something differently.

05

5-Axis LLM Completeness Scorer

one llm call, five axes, 0–50 total → percentage. qualitative view of overall input quality.
FROM IDEA 2

What it does: A single LLM call (separate from per-parameter scoring) evaluates the overall quality of the input across five dimensions. This produces the LLM Score component of the 3-part confidence formula. It catches things that parameter-state scoring misses — like whether features are described clearly enough to build, or whether boundaries are stated.

5 Evaluation Axes — each scored 0 to 10
Axis 1 — Feature Clarity: Are the features described precisely enough to build? (vague=0, specific=10)
Axis 2 — Scope Boundary: Is there clarity on what is NOT included? (none=0, explicit=10)
Axis 3 — User Role Definition: Are user roles and permissions even mentioned? (absent=0, detailed=10)
Axis 4 — Technical Constraints: Any technical requirements specified? (none=0, detailed=10)
Axis 5 — Missing Elements: How many expected parameters for this domain are unaddressed? (many=0, none=10)
// Formula
LLM_Score = (Axis1 + Axis2 + Axis3 + Axis4 + Axis5) / 50 × 100
// This becomes 30% of the final confidence score
06

GitHub Intelligence Layer — Semantic Search + Module Extraction

⭐ the killer feature from idea 1. validates ai-generated modules against real production codebases.
★ FROM IDEA 1UNIQUE

What it does: After domain classification, the system performs a semantic search over GitHub to find the 6-8 most similar real-world open-source projects. It then parses their README files and folder trees to extract actual module patterns used in production. This is the feature that makes the final module list grounded in reality, not just AI inference.

GitHub Search Pipeline — triggered after Step 1 (domain confirmed)

Sub-step A — Query Construction: Builds a GitHub search query from: domain label + top-5 project keywords extracted from P-01 and P-03 states + domain-specific filter terms. Example for a FinTech project with P-01 "payment processing for freelancers" and P-03 "invoice generation, payouts, tax reports": query = "fintech freelancer payment invoice payout open-source"

Sub-step B — Semantic Re-Ranking: GitHub search returns up to 30 results. The system embeds the project description and each repository's README (first 200 tokens) and computes cosine similarity. Top 8 by semantic similarity score are selected. This avoids false matches from keyword overlap alone.

Sub-step C — README Parsing: For each selected repo, the README is fetched and parsed for: section headers (## Installation, ## Features, ## API), feature lists (- [ ] feature), tech stack mentions (React, PostgreSQL, Redis), and integration names (Stripe, SendGrid, Twilio).

Sub-step D — Folder Tree Parsing: The top-level directory structure is fetched via GitHub API (or tree endpoint). Folder names like /auth, /payments, /notifications, /dashboard, /admin are extracted as raw module candidates. This often reveals modules that READMEs do not even mention.

Sub-step E — Module Candidate List: All extracted feature keywords and folder names become module candidates, each tagged with: source repo, extraction method (README header / folder name / feature list item), occurrence count across all 8 repos, and cosine similarity of source repo to the current project.

Example extraction — SaaS analytics project
  • Repos matched: Plausible, Metabase, PostHog, Umami, Ackee, Matomo (open-source), Nocodb, Redash
  • Module candidates from folders: /auth, /dashboard, /events, /reports, /team, /billing, /api, /settings, /onboarding, /notifications
  • From README feature lists: User authentication, Custom dashboards, Event tracking, Team management, CSV export, API key management, Email reports
  • High frequency modules (4+ repos): Auth (8/8), Dashboard (7/8), API (7/8), Settings (6/8), Notifications (5/8), Team (5/8), Billing (4/8)
07

Module Normalization, Fusion & Confidence Scoring

merges github candidates + parameter-inferred modules. deduplicates. scores each module by frequency and relevance.
MERGED

What it does: Takes two inputs — (A) the module candidates extracted from GitHub repos in Step 6, and (B) the parameter-inferred modules generated from the P-01 to P-09 state scores and domain template — and merges them into a single, deduplicated, confidence-ranked module list. This is where Idea 1's GitHub intelligence and Idea 2's parameter system converge.

Module Confidence Score Formula — per module
// Component A: Parameter Signal (does a matched parameter confirm this module exists?)
param_signal = max confidence of all parameters that map to this module (0–1.0)
// Component B: GitHub Frequency (how many of the 8 repos had this module?)
github_freq = (repos_containing_module / 8) weighted by avg repo similarity score
// Component C: Domain Template Match (is this module standard for this domain?)
template_match = 1.0 if module is in domain standard list, 0.5 if adjacent, 0.0 if absent
// Final module confidence
module_confidence = (param_signal × 0.45) + (github_freq × 0.35) + (template_match × 0.20)
// Deduplication: semantic similarity between module names > 0.80 → merge, keep higher confidence
if cosine_sim(module_embed_A, module_embed_B) > 0.80: merge, keep max confidence
// Output: ranked module list with confidence badges
> 0.80 confidence → HIGH (include with full detail in scope)
0.55–0.80 → MEDIUM (include with assumption note)
< 0.55 → LOW (include in "candidate modules" section, flag for client confirmation)

Effort sizing per module: Each confirmed module is also assigned an initial effort label (SMALL / MEDIUM / LARGE) based on: its complexity pattern in the GitHub repos (number of files, sub-directories), the domain template's complexity rating, and whether any special architectural patterns (real-time, ML, multi-tenant) were detected in the GitHub sources. This feeds directly into the effort estimation in Phase 2.

After Step 7, the system holds a fully grounded, confidence-scored module list. Every module on that list exists either because the client mentioned something that implies it, because real production projects of this type consistently have it, or both. This is vastly more reliable than any single-source approach.
Phase 2

Analysis & Scoring

Everything collected in Phase 1 is now computed into a single confidence number — one that actually means what it claims to mean, thanks to gates that prevent garbage from passing through.

Think of Phase 2 as the quality control checkpoint. You've gathered all the raw material. Now you measure it, check it for defects, score it honestly, and decide: is this good enough to show to the client? Or do we need to go back and ask more questions?
08

3-Component Confidence Calculation with BLOCKER + CRITICAL Gates

gates applied first. formula computed second. gate ceiling applied last. score means what it says.
FROM IDEA 2CRITICAL
Full Confidence Formula — v1 merged architecture
── GATE 1: BLOCKER ─────────────────────────────────────────────
IF P-01 OR P-03 state = MISSING:
  max_allowed_confidence = 40%
  DO NOT generate any scope output
  Show only BLOCKER question. BLOCKER rounds do not count against max_rounds.

── GATE 2: CRITICAL ────────────────────────────────────────────
IF any HIGH param (P-02, P-04) state = MISSING:
  max_allowed_confidence = 65%
IF all HIGH params ≥ PARTIAL-THIN:
  max_allowed_confidence = 100% (no artificial cap)

── COMPONENT A: COVERAGE SCORE (50% weight, structural, deterministic) ──
Coverage = Σ(param_score × param_weight) / Σ(max_weight × 1.0) × 100
  PRESENT → weight × 1.0 | PARTIAL-DEEP → weight × 0.7 | PARTIAL-THIN → weight × 0.3 | MISSING → weight × 0.0

── COMPONENT B: LLM QUALITY SCORE (30% weight, qualitative) ─────────
LLM_Score = (Axis1 + Axis2 + Axis3 + Axis4 + Axis5) / 50 × 100
  From Step 5. Unchanged.

── COMPONENT C: CONSISTENCY SCORE (20% weight, sanity check, NEW) ───
Consistency = 100 − |Coverage − LLM_Score|
  Coverage 80%, LLM 82% → Consistency 98 (agree → reliable)
  Coverage 80%, LLM 40% → Consistency 60 (disagree → retrieval or scoring failure)

── COMPONENT D: GITHUB VALIDATION BONUS (NEW — from merged architecture) ─
github_bonus = avg(module_confidence) × 5 (adds up to 5 bonus points)
  High-confidence GitHub module validation rewards inputs that map well to known patterns.

── FINAL FORMULA ─────────────────────────────────────────────────
Raw = (Coverage × 0.50) + (LLM_Score × 0.30) + (Consistency × 0.20) + github_bonus
Confidence = min(max_allowed_confidence, Raw)

── DOMAIN THRESHOLD ──────────────────────────────────────────────
Confidence ≥ domain_threshold → proceed to Phase 3 output path
Confidence < domain_threshold → proceed to Phase 3 questioning path
  Standard domains = 70% | FinTech/Healthcare = 80% | Internal Tool = 62%
  All thresholds stored in domain template config, not hardcoded.
09

Risk Detection Engine

pattern matching on module list, parameter gaps, and domain-specific architectural concerns.
MERGED

What it does: Scans the confirmed module list and parameter states to detect architectural risks, scope inflation signals, and common pitfalls for this domain. Risk detection runs even on low-confidence passes because risks can exist regardless of confidence level. Output is a risk list with severity (CRITICAL / WARNING / NOTE) used directly in the Stage 1 client output.

Risk Patterns Detected
  • Scope Explosion Risk: If module count exceeds 20 or the GitHub search found repos with team size 10+ and the current team estimate is 2–3, flag: "Scope appears to exceed team capacity. Consider phasing."
  • Real-Time Infrastructure Risk: If any module uses WebSocket, live tracking, streaming, or chat — flag: "Real-time features require WebSocket infrastructure. Budget for scaling and connection management costs."
  • MISSING Parameter → Architecture Risk: If P-05 (integrations) is MISSING but P-03 contains "payment" or "notifications" — flag: "Payment and notification integrations were mentioned but not specified. Stripe vs. Razorpay have different compliance requirements."
  • Multi-App Risk: If the domain classifier detects both mobile app and web platform signals — flag: "Building for both web and mobile simultaneously is 2.5× the scope. Consider mobile-first or web-first."
  • Domain Compliance Risk: For FinTech and Healthcare — always flag KYC/AML or HIPAA requirements as a WARNING regardless of whether P-10 is PRESENT, because non-compliance is catastrophic.
  • GitHub-Sourced Risk: If GitHub-sourced similar repos have more than 3 open "security" labelled issues in the same module — flag the module as having known attack surface concerns in production.
10

Effort Estimation Engine

sprint count, team size, story points, and confidence band. calibrated against github-sourced complexity data.
MERGED

What it does: Converts the confirmed, sized module list into a sprint breakdown and overall effort estimate. The key improvement in the merged architecture: effort is calibrated against the actual complexity observed in the GitHub-matched repos, not just a lookup table. A module that consistently occupies 40% of a codebase in similar real projects gets sized LARGE, even if the client described it in one sentence.

Effort Estimation Formula
// Step A: Base points per module size
SMALL module = 8 story points (simple CRUD, 1–2 day frontend, basic API)
MEDIUM module = 21 story points (auth, complex UI, webhook, async jobs)
LARGE module = 40 story points (real-time, ML, multi-tenant, payment engine)
// Step B: Complexity multipliers
domain_complexity = {FinTech: 1.4, Healthcare: 1.35, Marketplace: 1.25, SaaS: 1.1, Internal: 0.85}
// Step C: Team size velocity
team_velocity = {1: 13, 2-3: 26, 4-6: 45, 7-10: 60} story points per 2-week sprint
// Step D: Total
total_points = Σ(module_points × domain_complexity)
sprints = ceil(total_points / team_velocity)
// Step E: GitHub calibration adjustment
if github_matched_repos.avg_commits > project_avg: adjust +15% for underestimation bias
// Step F: Confidence band on estimate
if overall_confidence > 80%: ± 20% band on sprint count
if overall_confidence 60–80%: ± 35% band
if overall_confidence < 60%: "Estimate unreliable. Improve scope confidence first."
Phase 3

Loop or Output

The confidence score from Phase 2 dictates whether the system generates output now or runs a clarification round. Every loop condition is explicit. Diminishing returns detection prevents wasted rounds.

Think of Phase 3 as the decision tree. The system has done all its analysis. Now it either knows enough to produce a trustworthy output, or it knows exactly what's still missing and asks the client about it — intelligently, with multiple choice options, not open-ended blank boxes.
11

Threshold Decision & All Loop Exit Conditions

5 exit conditions. diminishing returns detection. blocker loops run indefinitely.
FROM IDEA 2
Exit Condition 1 — Threshold Met
  • Confidence ≥ domain_threshold (70% standard, 80% FinTech/Healthcare)
  • Proceed to Stage 1 output generation
  • All remaining PARTIAL/MISSING params are documented as assumptions
Exit Condition 2 — Max Rounds Reached
  • Default: max_rounds = 4 (configurable per domain)
  • If reached and still below threshold, generate output with confidence warning banner
  • All unresolved MISSING params listed in "What we still need" panel
Exit Condition 3 — Diminishing Returns
  • If confidence delta < 4% for 2 consecutive rounds → exit early
  • Note shown: "Further questions unlikely to improve confidence. Proceeding with current score."
  • Prevents useless rounds where the user answers but the pipeline doesn't improve
Exit Condition 4 — BLOCKER Unresolvable
  • If BLOCKER rounds exceed 5 and P-01 or P-03 is still MISSING
  • Flag for manual review. System cannot proceed.
  • Shareable link generated to send to the client for async completion
Exit Condition 5 — Client Override
  • Client clicks "Generate scope anyway" at any round (available after round 1)
  • Output generated with current confidence score displayed prominently
  • All assumptions made explicit in a Warning panel at top of Stage 1
Loop Decision Logic
IF BLOCKER_param_state = MISSING → BLOCKER round (pre-round, counter not incremented)
ELSE IF confidence ≥ domain_threshold → EXIT LOOP → Stage 1 output
ELSE IF round_number ≥ max_rounds → EXIT LOOP → Stage 1 with warning
ELSE IF delta < 4% for 2 consecutive rounds → EXIT LOOP → Stage 1 with diminishing returns note
ELSE → GENERATE MCQ questions for lowest-scoring MISSING/PARTIAL params → round += 1
12

MCQ Question Generation + Structured Reconstruction

multiple choice with domain scaffold options. no blank boxes. structured answers feed cleaner next run.
FROM IDEA 2

What it does: Generates max 3 questions per round. Questions are always multiple choice with domain-specific pre-filled options plus a custom text field. Questions are ordered by: BLOCKER first → HIGH weight MISSING → HIGH weight PARTIAL → MED weight MISSING. Answers are stored by question ID and formatted into structured context blocks before the next pipeline run — not appended as raw text.

☐ Product catalogue with categories & search ☐ Shopping cart & checkout flow ☐ Payment processing (Stripe / Razorpay / COD) ☐ Order management & tracking ☐ Seller / vendor management (marketplace mode) ☐ Admin dashboard & analytics ☐ Email / SMS notifications ☐ Reviews & ratings + Add your own: [custom text field always present]
B
BLOCKER check — if P-01 or P-03 MISSING, this runs first and only

Targeted BLOCKER question. MCQ format. Does not count against max rounds. Repeated (with different framing) until resolved. No other questions shown until BLOCKER lifts.

1
Run hybrid search + parameter scoring on enriched description

The full Phase 1 pipeline re-runs on the structured enriched input from the previous round. GitHub search only re-runs if domain changes or round 1. Subsequent rounds use cached GitHub results.

2
Recalculate confidence — check all exit conditions

New confidence calculated with fresh Coverage, LLM, and Consistency scores. Delta computed. All 5 exit conditions evaluated in order. If exit: proceed to output. If continue: generate questions.

3
Generate max 3 MCQ questions for the highest-impact MISSING/PARTIAL params

Questions prioritised by (param_weight × (1 − current_param_score)). Never repeat a question asked in a previous round. PARTIAL questions quote back the client's own words and target the specific gap — not generic options.

4
Structured reconstruction — format answers as labelled context blocks

Answers are NOT appended raw. Each answer is stored as: [Question ID] → [Selected options] + [Custom text] and formatted in a structured block that the pipeline can parse cleanly in the next run. This means each round produces genuinely better results, not just more text.

↺
Re-run full pipeline on enriched description — go back to Step 1

The enriched description (original + all round answers in structured format) is now the input for the next pipeline run. Confidence should meaningfully increase. If delta < 4% for 2 rounds, diminishing returns are detected and loop exits.

Final Verdict — What You're Building and Why It's Right

The merged ScopeAI architecture is the only design worth building because it eliminates the fatal weakness of each individual idea. Idea 2 alone produces a sophisticated, confident scope document — but built entirely from AI inference with no external validation. Idea 1 alone has the right instinct (check GitHub!) but no rigour around what to do with the information or how to iterate toward a reliable answer.

The merged version does all of it: it classifies the domain with three signals, chunks the input by topic not token count, searches both the input and GitHub simultaneously, scores confidence with gates that make the number honest, asks clarifying questions with structured MCQ options, reconstructs answers in a format that actually improves the next pipeline run, and produces two distinct documents — one that a client can read and approve, and one that an engineer can open on day 1 and start from.

  • ★ From Idea 2 (kept entire): BLOCKER/CRITICAL gates + 3-signal domain classifier + 9 domains + semantic-aware chunking + hybrid 4-stage search + parameter state system + 3-component confidence formula + MCQ questioning + structured reconstruction + diminishing returns detection + two-stage approval output + version history + config-driven architecture
  • + New from the merge: GitHub Validation Bonus in confidence formula + GitHub-calibrated effort estimation + GitHub-sourced risk flags + GitHub reference links in Stage 2 engineer doc + module confidence = param signal + github freq + template match (3-source formula)
  • ✓ Rating of the merged architecture: 9.8 / 10 — the remaining 0.2 is real-world calibration: synonym tables, domain entity dictionaries, and PARTIAL-THIN vs PARTIAL-DEEP thresholds will need tuning after the first 50 real client runs. That data only comes from building it.
